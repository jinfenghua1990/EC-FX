## 一、一页结论

### 1.1 现状（实测）

- **布局骨架已经存在**：`static/shell.html` 已实现「顶部一级菜单 + 左侧二级菜单 + 多标签 iframe」，并在本地 8050 生效（16:19 重启后 `/` 即外壳，版本 `2026.1027.1619`）。
- **但只到「骨架」**：6 个一级菜单、约 10 个二级入口；TAB 缺少未保存拦截、关闭其他/全部可关闭、详情独立 TAB、前进后退、权限校验；工作台可被关闭。
- **分销商档案只有 8 个业务字段**：编码、名称、联系人、电话、邮箱、区域、备注、启用；等级、审核、协议、返利、信用、应收、账号等全部没有。
- **没有任何认证与权限**：无 login / session / role / permission 代码，页面与接口全部可直接访问。因此「按权限展示操作」「TAB 不能绕过权限」「内外部账号分离」当前**一项都不成立**，不能靠加菜单或隐藏按钮冒充完成。
- **测试基线 39 个全绿**（命令与路径见 9.1）；项目无 git，只有物理备份。

### 1.2 本期建议范围

| 阶段 | 内容 | 归属 | 预估* |
|---|---|---|---|
| P1 | TAB 工作区达标 + 菜单注册表 + 历史/深链接 + dirty 拦截 | 窗口 C（外壳） | 2–3 人日 |

\* 单人估算，不含联调与用户验收；P1 与 P2 文件基本不重叠，可并行。

**本期不做、也不在菜单里假装可用**：采购与到货全块、发货任务/物流、分销商经营报表等（菜单显示「待开发」并禁用，见 3.2 方案 B）。

### 1.3 三条硬约束

1. 一套 FastAPI + 一套数据库 + 一套菜单注册表 + 一个外壳；不复制系统、不建重复业务表。
2. 菜单上的每个入口必须对应真实路由、真实表、真实接口；没有的标「待开发」，点击不进入空白假页。
3. 财务结果只能由单据计算，档案表不设可手工修改的应收/已付字段。

## 三、目标架构

### 3.1 总体

```
浏览器
 └── shell.html（唯一外壳：顶部一级菜单 + 左侧二级 + TAB 栏 + iframe 容器）
      ├── /api/nav            ← 菜单注册表（按权限过滤，P1 静态配置兜底）
      ├── /distribution…      ← 分销业务页（列表/详情）
      ├── /workbench …        ← 既有页面（embed=1 隐藏自带侧栏）
      └── postMessage SDK     ← dirty / 标题 / 页面状态 / 刷新拦截
FastAPI（单一应用）
 ├── /api/fx/*   分销域（P2/P3/P4 扩展）
 ├── /api/sys/*  认证与 RBAC（P5）
 └── SQLite（本地）/ PostgreSQL（群晖），同一套 Alembic 迁移
```

- **不引入前端框架、不重写 SPA**：现有 6 个页面都是独立 HTML + 内联 JS，重写风险远高于收益；iframe 恰好满足「切 TAB 不销毁页面」。
- **菜单单一来源**：菜单树只维护一份（优先后端 `/api/nav`，前端静态配置只作降级），杜绝「外壳一套、各页侧栏一套」继续分叉。P1 可以先由 `shell.html` 内 `MENUS` 提供，P5 接权限时迁到 `/api/nav`。
- **页面单一来源**：分销商列表/详情、订单列表/详情、价格、对账全部走同一套 `fx_*` 表与服务层，不建「界面专用表」。

### 3.2 菜单怎么呈现（需拍板，推荐 B）

| 方案 | 做法 | 评价 |
|---|---|---|
| A | 只显示已实现/部分实现的 5 个一级菜单 | 干净，但用户明确给了 9 个一级菜单的统一规划，且后续路线不可见 |
| **B（推荐）** | 9 个一级菜单全出；二级按真实状态标 `可用 / 部分 / 待开发`；待开发置灰，点击提示「功能规划中」，不进入空白页 | 既满足统一规划，又不把未开发说成完成 |
| C | 全出 + 占位页写「数据模型未建立」 | 容易被误认为“有页面=已完成”，不推荐 |

**推荐 B**，由菜单注册表的 `status` 字段驱动；上线前可用系统参数 `nav.show_planned` 控制是否显示待开发项。

```json
{
  "key": "dist",

  "icon": "🤝",

  "permission": "fx.distributor.view",
```

## 五、多标签 TAB 工作区详细规格

### 5.1 标签数据模型

```js
{
  version: 2,
  menu: "dist",              // 当前一级
  sideOpen: true,
  tabs: [
    {
      key: "t-...",          // 运行期唯一 id
      routeKey: "distributors",        // 稳定业务键（用于去重/恢复）
      url: "/distribution?embed=1&tab=distributors",
      label: "分销商档案",
      closable: true,        // 工作台 false
      dirty: false,
      stateKey: "distributors" // 页内状态桶
    }
  ],
  active: "t-...",
  history: ["t-...", "t-..."] // 可选，用于前进后退
}
```

持久化：

- 外壳状态：`sessionStorage["fx_shell_state_v2"]`（当前已是 v1，升级时做兼容迁移）。
- 页内状态：`sessionStorage["fx_page_state:<routeKey>"]`，由页面通过 SDK 主动写，外壳负责清理。
- 单个 tab 状态上限 64KB，总上限 512KB；超限丢弃最旧的非激活项并提示一次。

### 5.2 打开与去重规则

| 页面类型 | 规范 URL | 要点 |
|---|---|---|
| 列表/功能页 | `/distribution?embed=1&tab=distributors` | **筛选、页码、排序不进 URL 身份**，只存页内状态；重复点只激活已有 TAB |
| 分销商详情 | `/distribution/distributors/{id}?embed=1` | 每条记录一个 TAB；同 id 再次打开只激活 |
| 订单详情 | `/distribution/orders/{id}?embed=1` | 每条订单一个 TAB；列表点单号走独立 TAB |
| 其他既有页 | `/workbench?embed=1` 等 | 一页一 TAB |

- 判重键 = `path + 业务参数（id 等）`，**去掉 `embed` 与筛选参数**；避免「每换一个筛选条件就多一个 TAB」。
- 标签文案：菜单名；详情页为 `分销商 · {名称}` / `订单 · {单号}`；数据加载后可通过 `fxSetTitle()` 更新。
- 最高 30 个 TAB，超出提示先关；不做自动淘汰（避免丢未保存内容）。

### 5.3 关闭规则

- 工作台 TAB：`closable:false`，固定在第一位，不可关闭；「关闭全部」只关可关闭项。
- 关闭当前：优先激活右侧相邻，没有则左侧；全部关完显示空白引导。
- 标签右键菜单：关闭当前 / 关闭其他 / 关闭全部可关闭 / 刷新。
- 中键点击关闭（可选）。
- 关闭前若 `dirty=true`，弹确认；取消则不关。

### 5.4 未保存修改拦截（postMessage 协议）

子页面（`embed.js` 内置 SDK）：

```js
fxSetDirty(true|false);          // 表单变脏/保存成功后调用
fxOnBeforeClose(fn);             // 可选：自定义确认，返回 true 允许关闭
fxSetTitle("订单 · FX20261027001");
fxState.set("filters", {...});   // 页内状态（防抖 300ms）
const s = fxState.get("filters", {});
```

消息（同源 iframe，`postMessage` 必须校验 `event.origin === location.origin`）：

```
page → shell : { type: "fx:dirty", dirty: true }
page → shell : { type: "fx:title", label: "分销商 · 杭州某某" }
shell → page : { type: "fx:before-close" }
page → shell : { type: "fx:close-result", ok: false }   // 阻止关闭
```

- shell 在关闭/刷新前询问；800ms 无响应按「无自定义拦截」处理，避免卡死。
- 子页面不实现也可以：shell 依据 `dirty` 标志弹原生确认。
- shell 监听 `beforeunload`：有任一 dirty tab 时浏览器弹「离开此网站？」。
- **绝不做自动保存**；未提交内容不得因切 TAB 写入数据库。

### 5.5 页面状态保留

| 场景 | 机制 | 范围 |
|---|---|---|
| 切换 TAB 再切回 | iframe 常驻 + CSS 显隐 | 搜索词、筛选、页码、排序、滚动、已打开弹窗、未提交表单**全部天然保留** |
| 刷新浏览器 | sessionStorage 恢复 tabs + active + menu + 页内状态 | 列表筛选/页码/排序（页面接入 SDK 后）；滚动位置由 embed.js 记录/恢复 |
| 关闭 TAB | 清理该 tab 的 `fx_page_state` | 防泄漏 |
| 深链接/恢复时无权限 | 按 `/api/nav` 权限过滤后丢弃 | P5 |

P1 首批接入页内状态的页面：分销商列表、订单列表、对账（筛选 + 月份）。详情页表单**不做**自动恢复（避免把未保存数据误当已保存），只保留 dirty 标记。

### 5.6 前进 / 后退与深链接

- 打开/激活 TAB 时 `history.pushState({routeKey}, "", "/?menu=dist&child=fx-distributors")`；关闭 TAB 用 `replaceState` 修正。
- `popstate`：按 `menu/child/record` 查找已开 TAB，有则激活，无则按权限打开。
- 深链接规范：
  - `/?menu=dist&child=fx-distributors`
  - `/?menu=dist&child=fx-distributor-detail&record=12`
  - 直接访问业务页 `/distribution?tab=distributors` 仍然可用（独立打开，不依赖外壳）。
- 刷新后优先恢复 sessionStorage；URL 显式参数优先于恢复状态。
- 前进后退只切 TAB，不触发页面重新加载（iframe 已常驻）。

### 5.7 权限校验（P5，服务端为准）

- 每个页面路由、每个 API 都加服务端守卫（装饰器/依赖注入），不是只在前端隐藏。
- 菜单由 `/api/nav` 按当前用户权限过滤；TAB 恢复时再次校验，失效的直接丢弃。
- 直接手拼 iframe URL → 服务端 403；外壳显示「无权限」，不缓存该 TAB。
- 内部分销商详情接口必须校验数据域（防 IDOR：A 分销商不能看 B）。
- 分销商门户是独立登录域，不能进入内部 shell。

### 5.8 防止重复提交

- 所有提交按钮 `in-flight` 锁：请求期间禁用，失败恢复。
- 新建订单：`order_no` 服务端生成 + 唯一约束；重复请求最多产生一张（可加 `Idempotency-Key`）。
- 审核/推送：服务端先校验当前状态，非法状态返回 400，重复点击不会二次生效。
- 切 TAB 不会卸载 iframe，不会触发 `beforeunload` 提交；页面不得在 `unload` 时写库。
- 表单保存成功后才 `fxSetDirty(false)`；失败保持 dirty。

### 5.9 边界与异常

- iframe 加载失败：显示「重试」按钮 + 当前 URL。
- API 401：外壳统一跳登录（P5）；403：页内提示，不重试。
- 标签过多：横向滚动 + 滚轮横滚 + 激活项自动滚入视野。
- 响应式：≥1280 正常；900–1280 侧栏可收起；<900 侧栏浮层。
- 不支持的浏览器：提示使用 Edge/Chrome 最新版。

## 六、分销商档案升级

### 6.1 设计原则

1. `fx_distributors` 是主数据；订单、价格、收款、返利是业务单据，通过 `distributor_id` 关联。
2. 财务结果全部**派生**，不落可编辑字段。
3. 联系人在本期用字段（主/备/收货各一组），不建重复联系人表；将来需要多联系人再迁移。
4. 等级、区域用字典表 + 外键；现有自由文本 `region` 迁移为字典项后保留一版只读兼容。
5. 账号独立表，创建档案**不**自动创建内部员工账号，也不自动赋予内部权限。

### 6.4 财务口径（必须财务确认）

设 `D` 为某分销商：

- `total_purchase_amount = SUM(fx_orders.total_amount WHERE distributor_id=D AND status='approved')`
- `total_paid_amount = SUM(fx_receipts.amount WHERE distributor_id=D)`
- `total_rebate_amount = SUM(已确认返利金额)`（P4，来源返利核算记录）
- `current_receivable = total_purchase_amount - total_paid_amount - total_rebate_amount + 调整项`
- `unsettled_order_amount = SUM(approved 且未结清订单金额)`；P4 前无核销明细，先与 `current_receivable` 同口径并在 UI 标注「口径简化」
- `credit_available = credit_limit - current_receivable`（可为负，超信用预警）
- `last_order_at = MAX(order_date)`

约束：

- 以上全部服务端计算，接口响应只读；编辑接口忽略这些字段。
- 对账单金额、明细必须能回溯到订单/行；对账导出与页面汇总使用同一函数。
- 任何“调整”必须走单据并留痕，不允许直接改档案数字。

### 6.5 状态机与编码

审核状态（一次性）：

```
(pending) ──approve──> approved
    └──────reject─────> rejected
```

合作状态（生命周期）：

```
active ⇄ suspended        （暂停/恢复）
active ──> expired        （到期，可自动/手动）
active ──> terminated     （终止，保留数据）
```

- 新建（内部有权限）：`audit_status=approved`, `coop_status=active`，写一条系统初始化日志。
- 申请转入：`audit_status=pending`，审核通过后生成档案并置 `active`。
- 非法流转返回 400；每次流转写日志。
- 旧数据回填：`active=1 → approved/active`；`active=0 → approved/suspended`；不伪造审核历史。
- 编码：`FX` + 4 位序号（`FX0001`），基于当前最大序号 +1，唯一冲突重试 3 次；创建后不可改。批量导入允许携带编码（唯一校验）。

### 6.6 列表页规格

**列**：编码、名称、等级、联系人、电话、区域、合作状态、结算方式、信用额度、当前应收、最近下单、创建时间、操作。
**筛选**：关键词（编码/名称/联系人/电话）、合作状态、等级、区域、业务员；可组合。
**排序**：创建时间、最近下单、当前应收、信用额度（升/降）。
**分页**：20/50/100，服务端分页；默认 20。
**操作**（按权限）：查看详情（新 TAB）、编辑、审核（pending）、暂停/恢复（active/suspended）。
**不做物理删除**：终止合作用 `terminated`，保留单据关联。
**交互**：横向滚动、首列吸左、空态、加载态、错误重试、导出（权限）。

### 7.2 回填与兼容

- 旧 `fx_distributors` 行：`audit_status=approved`，`coop_status` 按 `active` 回填；不伪造审核人/时间。

- SQLite 加列用 Alembic batch 模式；新表不删旧表。

### 7.3 执行前检查

1. 备份数据库 `data/local/reconciliation.db`（带时间戳）。
2. 在副本上跑 `scripts/migrate.py`，核对行数与回填结果。
3. 同步 `update-manifest.json` 的 `database_revision` = alembic head，否则 `scripts/migrate.py` 会拒。
4. 版本三处同步：`VERSION` + `.env APP_VERSION` + `update-manifest.json`。
5. 迁移失败回滚：恢复备份（比 downgrade 更可靠）。

## 十、风险与待确认

### 10.1 风险

1. **无 git 兜底**：项目是本地副本，每阶段前物理备份（代码 + `data/local/reconciliation.db`）。
2. **权限是硬前置**：P5 前无法满足 3 条权限验收；不要把「隐藏按钮」当权限。
3. **两窗口并行冲突**：C 主改 `shell.html`/`embed.js`；A 主改分销后端/页面；共享 `main.py` 时先读后改、登记认领。迁移编号先认领。
4. **iframe 方案边界**：前进后退/深链接/dirty 都要额外协议；但比 SPA 重写风险低。若未来要彻底 SPA，另立项目，不半途混用。
5. **菜单全量展示**：方案 B 会看到不少「待开发」，需用户接受；否则改用方案 A。
6. **财务口径需财务确认**：应收是否含税、返利何时冲减、预付款处理、调整单规则。
7. **旧页面数据口径**：`/sales-outbound`、`/shipments` 是旺店通/历史数据，不隶属分销订单；菜单里要注明「历史/出库」而非「分销发货」。
8. **文件上传**：目录、备份、权限、病毒/类型限制；必须纳入 `preserve`。
9. **性能**：30 个 iframe 上限；列表服务端分页；SQLite 并发写有限，群晖 PostgreSQL 需回归。
10. **sales-outbound 乱码**：1,539 个 U+FFFD，需重建文案；不要用错误编码批量“修复”导致二次损坏。

### 10.2 需要你拍板（5 件）

1. **菜单呈现**：A 只显示可用 5 组 / **B 全 9 组 + 待开发置灰（推荐）** / C 全出 + 占位页。
2. **起步顺序**：**P1 TAB 与 P2 档案并行（推荐）** / 先 P1 / 先 P2 / 先 P5 权限。
3. **权限时机**：P5 本期做（能满足全部验收）/ 延后（先接受权限项不达标）。
4. **首发范围**：分销商档案 + 详情 11 页签是否本版必须；采购到货/发货/报表是否确认放 P6。
5. **财务口径**：应收/已付/返利/信用额度的计算与冲减规则，需财务确认（可先按 6.4 默认口径）。
